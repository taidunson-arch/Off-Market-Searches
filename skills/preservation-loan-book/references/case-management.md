# Persistent HFA case management

The local SQLite operations database now stores durable case ownership, work due
dates, status, completion submissions, independent review decisions, named
escalations and append-only change history. Pipeline imports reuse existing cases;
they do not overwrite officer decisions or reopen completed work.

## Operating the queue

Configure `operations_db` in the pipeline configuration. Generated deadline cases
start OPEN and unassigned: the pipeline knows an agency role, not the identity of
the responsible staff member. The queue exposes `unassigned` for supervisor triage.
Use the same database path on subsequent runs.

```sh
python scripts/manage_cases.py --db agency.sqlite list --as-of 2026-10-04
python scripts/manage_cases.py --db agency.sqlite list --as-of 2026-10-04 --owner "Alex Officer" --due-by 2026-11-01
python scripts/manage_cases.py --db agency.sqlite list --as-of 2026-10-04 --status PENDING_APPROVAL
python scripts/manage_cases.py --db agency.sqlite list --as-of 2026-10-04 --escalated-to "Pat Director"
python scripts/manage_cases.py --db agency.sqlite show CASE_ID
```

`show` returns the current case, all evidence records, review decisions, complete
audit history, manual case scope and originating action snapshots. Closed and
cancelled cases remain stored; add `--include-closed` when listing them.

Staff can create work that is not generated by a calendar event:

```sh
python scripts/manage_cases.py --db agency.sqlite create --run-id RUN_ID --property-id PROPERTY_ID --instrument-id loan:LOAN_ID --title "Review reserve shortfall" --due-date 2026-11-01 --owner "Alex Officer" --actor "Sam Manager" --priority HIGH
```

The property and optional instrument must belong to that saved run. Omitting the
instrument intentionally creates property-level work. Manual cases appear in the
case view's `scope`; generated cases are traced through the immutable `actions`.

## Changes and independent review

Every change requires the current version from `show` or `list`. A successful
change increments the version and returns the updated case; a stale version is
rejected without adding evidence or partial history.

```sh
python scripts/manage_cases.py --db agency.sqlite change CASE_ID assign --actor "Sam Manager" --version 1 --value "Alex Officer"
python scripts/manage_cases.py --db agency.sqlite change CASE_ID start --actor "Alex Officer" --version 2
python scripts/manage_cases.py --db agency.sqlite change CASE_ID submit --actor "Alex Officer" --version 3 --evidence "dms://reserve-review/123" --value "Signed statement and bank reconciliation"
python scripts/manage_cases.py --db agency.sqlite change CASE_ID approve --actor "Sam Manager" --version 4 --evidence "dms://approval/456"
```

Only the named owner can submit active work. Submission requires completion
evidence and changes status to PENDING_APPROVAL. A separate reviewer approves or
rejects that exact submission. Names are compared without case or whitespace
differences. `reject` requires a reason and returns work for correction; resubmitting
creates a new evidence record. Prior submissions and decisions are retained.

The approval record stores the completion evidence ID, submitted version, reviewer,
time and review evidence. Successful approval closes the case and records its
completion time. Pending submissions cannot have their owner, due date or priority
changed before review. Escalating a pending submission withdraws it from approval
and retains its evidence/history; a fresh submission is then required.

## Deadlines, evidence and escalation

| Operation | `--value` | `--evidence` | Behavior |
|---|---|---|---|
| `assign` | Named owner | Optional | Changes responsible officer |
| `reschedule` | ISO work due date | Required reason | Retains original obligation date |
| `priority` | LOW, NORMAL, HIGH or URGENT | Required reason | Changes triage priority |
| `attach` | Optional description | Document/reference | Adds an immutable evidence record |
| `note` | Optional context | Note text | Adds an immutable note |
| `submit` | Optional description | Completion reference | Owner submits for review |
| `approve` | Optional review note | Approval reference/rationale | Independent reviewer closes work |
| `reject` | Optional review note | Correction reason | Independent reviewer returns work |
| `escalate` | Named recipient | Required reason | Records recipient, reason and time |
| `deescalate` | Optional | Resolution reason | Clears active escalation; retains history |
| `cancel` | Optional | Required reason | Cancels without claiming completion |
| `reopen` | Optional | Required reason | Reopens while preserving old evidence and decisions |

`due_date` is the staff work deadline. `original_due_date` and originating action
dates retain the source obligation: rescheduling work does not amend a loan,
contract, covenant or statutory deadline. The audit shows both dates before and
after the change. Imports preserve this distinction.

Escalation records and filtered queues provide persistent handoffs; this release
does not send email or notifications. Evidence entries preserve references and
notes, not document bytes. The referenced DMS must retain access and document
versions; recording a reference does not verify its contents.

## Migration and controls

Opening an existing database applies transactional schema version 3. Existing
case IDs, statuses, owners, versions and audit rows remain intact. Old completion
evidence strings are retained and copied into evidence records marked
`legacy_import`. Their new capture timestamps are migration times, not invented
historical submission times. Existing historical review decisions remain in the
old audit; the migration does not manufacture new approval records.

Evidence, review decisions and manual scope records reject updates and deletes.
Changes run in a transaction with optimistic version checks and SQLite write
serialization. Foreign keys prevent cross-property manual scope and cross-case
review evidence. Application errors roll back state, evidence and audit together.

This is a single-agency local tool. Actor names provide attribution and workflow
separation, not authenticated identities or role-based access. A database owner
can bypass application controls. A shared production service still needs identity,
authorization, backups and a retained document store. Back up existing databases
before migration.
